# Explaining Aurelle's agent architecture in an interview

## The short version

Aurelle is a bounded shopping assistant built from deterministic application services, a real embedded vector database and optional LLM decisions/narration. Not every turn is sent to a language model. We deliberately choose the cheapest reliable execution path for the user's intent. A language model is an interpreter/writer, not the source of prices, availability or database permissions.

## Why an answer can arrive in about 100 ms

Consider `szukam czegoś do domu za około 29$ mniej więcej`.

1. The browser sends the conversation to the Next.js POST endpoint.
2. The endpoint validates roles/parts, restores canonical product facts, applies the conversation guard and the production admission policy, and resolves the configured provider. Local llama.cpp provider resolution may make a model-discovery HTTP call; Groq configuration is local setup only.
3. Application code detects an approximate amount of 29 and USD, plus home-shopping context. It chooses structured browsing, not semantic text retrieval and not an LLM planning call.
4. LanceDB opens/reuses its prepared table, filters the relevant catalog and returns candidates. For an approximate target the tolerance is max(EUR 5, 20% of target), and absolute distance from the numeric EUR reference controls order. `Around` does not mean `at most`.
5. Foreign-currency handling disables optional LLM wording in this case. The application emits verified product cards plus explicit EUR-budget confirmation. It does not claim that USD 29 equals EUR 29 and does not fetch an exchange rate.
6. The AI SDK stream protocol delivers those parts to the React client. A stream is a transport format; it does not prove that tokens were generated by an LLM.

That path can take only milliseconds after initialization. HTTP, validation, UI work and network latency add overhead. A user-observed 100 ms is plausible; no response cache is implemented and we cannot reconstruct the exact historical timing without a trace.

## Three different kinds of reuse

| Mechanism | What is reused | What it is not |
| --- | --- | --- |
| Disk model cache | Downloaded, pinned ONNX weights/tokenizer files | A cache of customer answers |
| Ready LanceDB index/table | Previously computed catalog vectors, stored product records and an open table handle | A saved generated reply |
| Loaded encoder | One initialized CPU inference session per repository/worker | A result cached for the last customer query |

Catalog indexing runs once for a catalog/model fingerprint. Semantic queries still compute their own query embedding. Structured browsing needs no query vector. Warm access avoids download/initialization/reindexing, not the actual relevant query.

## Execution paths

| Turn | Planner LLM | Query embedding | Database | Optional narration |
| --- | --- | --- | --- | --- |
| Greeting / language preference | No | No | No | No |
| Known product ID | No | No | Canonical lookup | No |
| Category list | No | No | Repository category list | No |
| Price-only or broad home request | No | No | Structured LanceDB browse | Usually, if products exist and currency is EUR |
| Clear morning-coffee shopping need | No | Yes | Cosine vector retrieval | Yes when enabled |
| Other free-form shopping question | Yes | Depends on selected validated tool | Depends on tool | For successful search |
| USD/other foreign-currency approximate browse | No for recognized generic browse | No | Structured price-reference ranking | No; explicit currency confirmation |

The model supports more utterances than the structured rules. It emits a whitelisted Zod-validated action: search, details, categories, policy, conversational response or refusal. Unknown/invalid actions ask for clarification instead of executing arbitrary code. This is not a model-controlled SQL console, recursive agent swarm or autonomous checkout engine.

## Retrieval versus generation

The catalog is English. The planner translates a free-form multilingual search need into an English semantic query when necessary. BGE or MiniLM encodes that query using the exact same embedding space as the indexed descriptions. LanceDB compares vectors by cosine distance; structured constraints such as price/category/exclusions are independent filters. A small catalog uses exact nearest-neighbor retrieval rather than a costly approximate index.

BGE q8 and MiniLM q8 have separate pinned weights, pooling conventions, prefixes and relevance cutoffs. Sharing 384 dimensions does not make their vectors interchangeable. The table fingerprint includes the catalog and encoder identity, so changing price/stock/model builds another derived table.

The configured Groq model is `openai/gpt-oss-120b`. Groq is the inference provider; it is not xAI Grok. The 120B parameter count describes its remote model, not RAM consumed on Render. The local encoder is about 23 MiB of MiniLM weights (or about 34 MiB for BGE); process RSS is larger than weights because Node, ONNX and native libraries also occupy memory.

## Conversation state has four boundaries

1. **Visible conversation:** shared root ChatProvider keeps messages and in-flight state during product navigation. Versioned localStorage keeps settled messages and draft across reloads. Incomplete tool parts are not replayed; product cards rehydrate against current catalog records. This is device-local, not an authenticated cross-device history store.
2. **Conversation lifetime:** 20 customer messages or 24000 textual characters closes the composer. The final allowed turn can finish; a visible completion notice invites a new conversation and keeps the cart. A warning appears for the last three turns. Restarting a topic creates a new Chat instance; late old responses cannot populate it.
3. **HTTP context:** validated settled parts are bounded to a smaller request history and about 80 KB, with a 100000-character request-body guard. The API independently rejects excessive turn/character submissions with HTTP 409 before model/database work. This is an application policy, not an exact measurement of model tokens; a public stateless client can still start a new conversation or alter its local transcript.
4. **LLM context:** compactModelHistory retains up to 12 recent model messages and at most 6500 JSON characters, shortening earlier text and replacing full product records with concise IDs/names/input summaries. Prompt instructions and output allowance add their own budget. Characters are not tokenizer-exact tokens. We deliberately stay small rather than attempting to use a remote model's full context window. This is lossy compaction, not a hidden LLM summary or long-term memory.

Context-window capacity, an upstream per-minute token quota and per-hour application limits are different constraints. You can hit a free Groq TPM limit even while staying far below its context window. A restart may reset in-memory app quotas; it does not reset the provider's organization quota.

## Error, cost and scope boundaries

- A 90-second overall request deadline and an eight-second optional narration deadline prevent endless model waits. Browser Stop cancels; New conversation also isolates state.
- Tool inputs are typed/validated and cannot name arbitrary database tables, URLs or shell commands.
- Product facts come from canonical records; price ceilings and approximate ranking run in TypeScript/LanceDB, not model arithmetic. There is no automatic FX conversion.
- Optional narration writes conversational framing and a relevant follow-up question. It rejects digits/currency amounts, URLs and selected contradictory claims; a safe grounded reply remains if it fails. Such checks reduce risk but are not proof against all hallucinations or prompt injection.
- Production has two concurrent requests and 120 valid chat POSTs per rolling hour per process. Retries count, health GETs do not. These are in-memory demo controls, not authentication, distributed protection or a provider billing cap.
- `/api/health` tests Node liveness without paying for a model request. The deployment verifier separately exercises real retrieval and an LLM-selected policy tool.
- `[AGENT] trace` logs selected path, operation, attempted LLM calls, elapsed execution milliseconds and `responseCache:false`, without the whole conversation or credentials. It measures stream execution; HTTP middleware/provider discovery/transport/render time is outside that span. A fallback narration attempt still counts as a call attempt.

## Development stability

The previous Turbopack development process became unresponsive and was observed around 3.8 GiB RSS; this is a measured symptom, not proof of a particular Next.js memory leak. Development now uses Webpack and `.next-development`, isolated from `.next` production/type/build outputs. The failing owned process was restarted. This avoids mixing generated trees while keeping the optimized production build and Docker workflow intact.

## Honest interview positioning

Say: “I built a hybrid bounded agent: deterministic business invariants and optimized common paths, model-driven interpretation for other requests, actual vector retrieval, typed tools, and optional language generation. I can identify which path answered a turn and test it independently.”

Do not say: “Every response is generated by a 120B model,” “vector search always runs,” “there is no backend,” “we cannot exceed any quota,” “we count tokens exactly,” or “localStorage makes the history trustworthy.” These claims would be inaccurate. The interesting engineering is deciding where probabilistic behavior is useful and where predictable application code should take control.

## Retry and the durability follow-up

The browser's Retry last message calls AI SDK `regenerate()`. It does not append another customer turn: the failed answer is regenerated using the same normalized conversation, current catalog and selected provider. A browser regression first returns HTTP 503, then a valid stream, and asserts identical POST bodies and one user message. Retry still counts toward application/provider quotas.

It can help after a transient connection error, a recovered provider or a one-off generation failure. LLM sampling may also yield different valid wording/action on a repeated attempt; that is not a promised recovery strategy. The adapter does not secretly change models or automatically spend repeated calls. Clicking immediately cannot fix a depleted daily quota, invalid key, unsupported model or context-limit closure; the underlying condition must change. For a stopped/incomplete saved response, Resume response has the same general regeneration meaning.

The reported `trwałość materiału` exchange was reproduced with real Groq and completed at inspection time, so the historical transport error cannot be attributed conclusively. The response also exposed an evidence problem: catalog descriptions do not establish impact resistance or wall thickness. A bounded evidence-specific handler now recognizes durability follow-ups in a vase conversation, states the missing evidence rather than promising durability, and asks whether daily use or dropping is the concern. It deliberately avoids an unnecessary provider dependency for facts the catalog cannot supply. This handler covers the named scenario; it is not a general product-material expert.

## Concrete measured fast-path example

On the repaired development server, replaying `szukam czegoś do domu za około 29$ mniej więcej` returned the ceramic vase at EUR 32 and amber glass vase at EUR 25. The execution trace reported `route: structured`, `operation: searchProducts`, `llmCalls: 0`, `elapsedMs: 96`, `responseCache: false`. The complete development HTTP log was about 579 ms in that run, including compilation/request handling. Do not confuse the execution span with full browser-perceived latency or claim every request is 96 ms.
