# Aurelle agent architecture

Aurelle is a shopping assistant for a demo catalog. A configured language model interprets customer requests and uses native tool calls; application code owns tool execution, catalog facts, selection checks and cart rules. The 86 products, prices, stock, specifications and store policies are authored demo data.

## A conversation turn

The chat endpoint validates the message history, optional device-cart snapshot and request limits. It restores the latest validated shopping checkpoint and passes up to twelve recent role-labelled messages, a compact shopping state and the current request to the model. Up to six prior result groups link earlier choices to canonical product IDs and names. An old transcript in localStorage is discarded on upgrade. The state contains language, scope, criteria, preferences, requested count, shown and rejected IDs, recent selections and comparison IDs. It is a preference and conversation hint, not a source of product facts. The optional cart snapshot contains device-local IDs and quantities; it does not create a server-side cart.

A general capabilities question can finish in one tool call. For an explicit comparison of two named products, the application resolves both full catalog names in request order. A lookup for one exact product can complete its promised detail read directly. Product references, catalog summaries and presentation validation live in the application layer. Groq transport and request accounting live in infrastructure.

The model can describe its supported shopping capabilities, search, list categories, fetch product details and policies, compare products and propose a cart update. Each tool has a schema and is executed by the application. Catalog operations commit their canonical result, product group and checkpoint before optional advice. Structured UI actions execute the same services without interpretation or presentation inference. A free-form interpretation can finish with `presentAnswer`; after an executed read, dedicated optional advice is plain buffered text with no tools and cannot alter the committed view, IDs, counts or prices. The server validates the citations, referenced products and supported absence claims and resolves supported price, count and measurement references against recorded evidence. A model may answer a greeting or ask a clarification without searching. A confirmation can keep its natural text without repeating cards. When recommendations are presented, the application restores the complete verified page if the model omitted presentation IDs. The model cannot execute arbitrary code or write browser storage.

A turn is limited to four model inferences, with at most 1,024 output tokens for interpretation and 192 for optional advice. One correction is available for an invalid interpretation; optional advice has no correction or regeneration. Dedicated advice receives only canonical material, features and limitations, without raw prices or dimensions. Unmeasured size/performance comparisons are rejected. Advice is buffered, limited to 400 characters and rejected on incomplete/provider-filtered endings, wrong language, unbalanced punctuation or unsupported numeric references. Counts use typed evidence fields and group length rather than a census of digits in serialized JSON. Monetary/difference/dimension references resolve against canonical fields. Enumeration is not a catalog fact. The Groq adapter requests low reasoning effort for GPT-OSS 120B and disables parallel tool calls. Provider support for these options and the quality of interpretation remain model-dependent. A provider failure before the requested operation completes is reported as an operation failure. A successful catalog result remains completed if its independent advice is unavailable. The AI request deadline is thirty seconds; attempt and quota-wait limits remain shorter.

## Search and evidence

Product prices, stock and store policies belong to the catalog domain. The application layer resolves shopping transitions, assembles recent selections, verifies model claims against evidence and produces a customer summary. Infrastructure handles vector retrieval, provider calls and typed streaming. The chat and catalog composition roots select their respective adapters. Presentation owns the transcript, cart receipt and retry controls.

A details request reads the canonical record. Direct questions about stored fields can finish with that read. For a descriptive feature or missing specification, a compact follow-up can select a complete supporting fact from the same record. The application checks the cited field, numbers, units and supported limitations before displaying the answer. If the model or catalog cannot establish the requested information, the shop preserves the product and explains the uncertainty.

Search transitions distinguish a new search, refinement, change, alternatives and browsing. Functional needs use canonical seating, coffee or music groups whose full type membership is expanded by application code. Explicit kind, subtype, department and type exclusions need evidence from the current request or an unchanged established constraint; an arbitrary subset cannot silently remove previously shown types. The model proposes the transition; application code validates it and merges or resets typed criteria. Shown IDs support alternatives. A rejection requires a quoted fragment of the current request referring to that product or group; merely showing a product does not reject it. Explicitly rejected IDs are kept separately. A new topic can reset unrelated search conditions while explicitly persistent preferences remain. The model can still misunderstand a request, so these mechanisms are boundaries rather than guarantees of interpretation.

Search has separate recommendation and lookup modes. A recommendation resolves the active criteria once per user turn; independent lookups can resolve named products before a comparison without changing those criteria or advancing a result page. An erroneous overview during an explicit comparison of grounded subjects redirects to a product lookup. That recovery discards inherited recommendation filters and uses the current translated query; the existing facet resolver restores constraints actually stated in the current request. The model can choose subsequent reads within the inference budget.

LanceDB retrieves matching IDs. The repository hydrates those IDs from the same catalog records used by product pages, comparison and chat cards. Policies such as delivery price and returns duration have a shared domain source. LanceDB filters category, kind, type, environment, price, stock, excluded types and required recorded features before semantic ranking. The Garden category is a merchandising grouping; outdoor furniture uses the furniture kind and outdoor or both-environment records across categories. `maxPrice` is a hard EUR ceiling. `targetPrice` uses a tolerance of the greater of EUR 5 or 20% and sorts by distance from the target. The application has no exchange-rate service.

Required features use exact normalized properties and reviewed material-composition mappings. Glazed ceramic satisfies ceramic and amber glass satisfies glass; brass-finish metal does not establish solid brass. Known Polish catalog terms are rejected before entering the English encoder so the model can translate its query once. A substring in a description or limitation is not proof of a feature. Unsupported certification, waterproofing or other unrecorded facts cannot be inferred from a product's absence of limitations.

A search normally requests five products and returns at most ten per page. `SearchEvidence` records the applied criteria, outcome, requested count, scope total, total matches, unseen matches before the page and remaining matches after it. Counts allow a short page, no match or exhausted result to be described from actual evidence. Category cards contain a name, count and canonical example ID for each of the ten categories. Comparisons accept two to ten distinct catalog IDs and calculate cheapest IDs and price differences in cents from canonical prices.

## Stream, history and compatibility

The storefront opts into `shopping-v3`. The stream carries text plus typed `data-products`, `data-categories`, `data-comparison`, `data-shoppingState` and `data-turnStatus` parts as appropriate. A checkpoint includes the before and after state and the user-message ID; a client can restore it after navigation or reload. Card details are resolved from the current catalog. `data-operation` is a discriminated union of completed, needs-input, awaiting-device and failed. `data-advice` independently reports not-requested, included or unavailable with an optional absolute retry deadline. Legacy status is derived from the operation alone. A completed operation cannot contain its own error. Advice retry uses the completed operation ID and canonical snapshot, including after reload, and never repeats search, pagination or a cart proposal.

The same engine has adapters for `shopping-v2` and earlier consumers. The v2 adapter emits legacy tool-result shapes and supports single-item cart actions. Earlier clients receive legacy result arrays and use product-card controls. The current UI can render validated legacy history alongside the newer data parts. Old results containing cards or a comparison plus a failed presentation are normalized to a canonical completed result; truncated assistant prose is removed. The session transcript retains message IDs, draft, groups and receipts. The cart and its operation ledger remain in persistent device storage. Incomplete tool calls are not replayed from stored history.

The conversation is limited to 20 customer messages or 24,000 textual characters. The API validates history independently and limits incoming request size. Model context is compacted separately; these are application limits, not authentication or an exact provider-token budget. Retry resends the same user turn, while a stopped or replaced stream is isolated from later cart effects.

## Cart actions

Known explicit cart instructions resolve their operand and quantity deterministically; harmless commentary does not change authorization. The model may propose up to ten items for compound read-and-add requests only in response to an explicit add request. Application checks authorize the referenced selection and requested quantities against the request and shopping state. Ambiguous selections and ties require clarification. The process keeps at most one pending intention per conversation, with a nonce, source message, question kind, eligible products/quantities, language and ten-minute expiry; the map is bounded to 300 entries and cleaned during requests. The checkpoint nonce alone cannot authorize a write. Yes resolves only a live fixed confirmation, never an unresolved product choice. Topic changes, refusal, conflicting requests and expiry invalidate the intention; restart requires a fresh choice or quantity. Stable cart operation IDs use the source request, while emission still binds to the current active user turn. Unavailable selections require input; an unavailable item prevents the proposal. The typed action retains the legacy first `productId` and `quantity` and may include an `items` array.

An operation ID derives from the conversation and user-message IDs. The browser accepts a proposal only from the matching active stream, checks stock and line limits, and saves the cart, operation ledger and receipt in one local storage write. It reports an addition only after that write succeeds. A repeated operation is idempotent, and a multi-item operation is applied atomically. The cart remains on the device and is not an order, payment or checkout.

A failed local save offers a manual retry of that same action without another model request. Restoring history never executes it automatically. After reload, a failed action requires a fresh user request; successful receipts remain readable and the ledger prevents duplicate additions.

## Embeddings and index

The catalog has 86 products across ten categories. Each record contains a short description, fuller specifications, canonical type and kind, environment, material, dimensions, features and limitations. Purpose and detailed documents are embedded independently, averaged with equal weight and normalized. Structured browsing does not require a query embedding.

| CPU profile | Model | Pooling and query prefix | Cosine-distance cutoff |
| --- | --- | --- | --- |
| `bge` | `Xenova/bge-small-en-v1.5` | CLS; retrieval instruction prefix | 0.45 |
| `minilm` | `Xenova/all-MiniLM-L6-v2` | Mean; no prefix | 0.74 |

Both profiles use pinned q8 models and normalized 384-dimensional vectors. After structural filtering, the accepted distance is the smaller of the profile cutoff and the best eligible neighbor's distance plus 0.2. The Docker profile uses MiniLM.

A content-addressed LanceDB table fingerprint includes the full catalog, encoder identity, actual indexing documents and representation version. The explicit tokenizer loading fix does not change these fingerprint inputs, encoder revisions or vector representation. The tokenizer JSON and configuration are fetched directly at the pinned revision into the model cache when missing, then loaded with the pinned model. A populated cache can therefore support offline startup; an absent tokenizer file fails when remote model access is disabled. Local model files and tables are caches, not customer responses.

## Operations and verification

One server-only configuration selects the direct Groq endpoint, shop credential and immutable model for every public inference. Retry reuses the original user turn. The application preserves a completed catalog result when only optional advice fails. A local QA override requires explicit loopback binding and a loopback peer, and is rejected on Render. Successful inference traces record the model ID returned by Groq. Request, inference and terminal events can be correlated by attempt and operation without logging the conversation or credential. Per-instance admission limits count requests and retries, reset on restart and do not replace provider quota controls. Successful Groq token-limit headers inform an estimated reservation before the next inference, including simultaneous requests. Waiting is cancellable and stays within the endpoint deadline. External traffic or estimation differences can still cause a 429; `Retry-After` establishes a shared cooldown without an automatic retry. `/api/health` reports liveness, revision, embedding profile and prepared-index metadata without calling the model.

`npm run test:agent:dry` scripts native model responses while using the actual MiniLM encoder and LanceDB. The Docker smoke uses a native tool fixture and checks the container and index. `npm run test:agent:live -- <url>` exercises the configured running provider; its cart writes are simulated. Browser acceptance must separately verify the real device-storage flow. These checks establish different evidence and none guarantees future provider behavior. See the [README](../README.md) and [hosting](HOSTING.md) for commands and configuration.

A recommendation declares its planned continuation. A completed ordinary recommendation commits its application result before one optional plain-text advice inference; lookup mode remains adaptive for independent reads and comparisons. Rejected native calls and SDK tool-choice violations share the bounded correction path and finish as partial when the budget is exhausted. Captured successful HTTP response usage includes billed responses that the SDK later rejects for protocol violations, with SDK usage as a fallback. A virtual preferences citation can recall the user's typed budget without treating it as a product price.

All starters, examples and contextual controls carry validated structured actions in user-message metadata. Catalog actions work independently of model initialization and model cooldown. Advice controls request a separate inference for the completed result. Current natural language overrides older language choices; UI text/product names retain the conversation language, and short confirmations use the pending question language. It retains the displayed product group across single-product inspection. Transient stream progress starts before model execution, and handled failures finish with one typed status, an absolute retry deadline and any already verified catalog results. Cooldown survives reload independently of conversation/cart storage; it blocks AI advice retry while catalog controls, known cart operations and draft editing remain available. Typed HTTP admission failures persist against the proper user message and do not become failures of a new conversation.
